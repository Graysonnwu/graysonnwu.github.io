# 字幕综合工具改进与颜色实验（2026-10-04）

本轮找到了旧工具的确定性问题，也复现了「截图原始 RGB 很接近、浏览器实际取色却不同」的现象。尚未重现用户某个真实视频的原有色差，不能宣称 IINA 与 FFmpeg 已经普遍一致。

## 已修改

- 默认颜色映射改为 RGB 原样转 ASS BGR。历史 0→0、74→85、163→170、253→255 公式作为明确标注的旧实验选项保留。
- 目标色直接保存 RGB，HSV 滑块采用小数精度。原工具把计算得到的小数 HSV 写进整数步长滑块，读回时会改变目标色；现在初始 `#EB8330` 输出准确的 `\1c&H3083EB&`。
- 加入外挂字幕/压制成片配对截图、浏览器 sRGB 的 5×5 中位数取色、通道跨度和 PNG 的 cICP/gAMA/sRGB/ICC 描述提示。
- 加入每次流程独立的三维仿射校准、训练 RMS、最大残差、逐个留出验证、灰阶/退化样本拒绝、超色域截断及外推提示。导入/导出 JSON 保留样本和流程记录。
- 同时输出覆盖标签和 Style 的 AABBGGRR 值，保留真实输出不被复制提示暂时覆盖；复制失败时选中文本并提示手动复制。
- 坐标工具按 ASS PlayRes 换算截图坐标，修复居中窄图的十字线偏移；改善图片解码/无效文件、对象 URL 回收、无效尺寸和键盘操作。
- 补充手机视口、侧边栏、表格和截图区的缩放布局。Sub/sub 的两个 HTML 源由同步脚本输出为独立文件，未改真实字幕、视频或渲染流程。

## 夹具与版本

- FFmpeg 8.1（本机 `ffmpeg-full/8.1_1`），libass 0.17.4 / API `0x1704000`；脚本保留 libass 日志及精确视频属性。
- IINA 1.4.2，mpv v0.38.0，libass 0.17.2 / API `0x1702000`（运行时 libass-version 为 24125440）。
- 1280×720、24 fps、6 秒、H.264/yuv420p、BT.709 原色/传递/矩阵、limited 范围，24 个不透明矩形 ASS 色块。无字体、描边、透明边缘干扰。
- IINA 临时 `sub-ass-override=no`，`sub-ass-vsfilter-color-compat=basic`，`screenshot-tag-colorspace=no`；视频解码为 VideoToolbox。精确运行属性在本地 `output/iina-capture.json`。

## 先分清截图口径

FFmpeg 输出 PNG 带 `cICP = [1,1,0,1]`、`gAMA=0.45455`、cHRM；IINA 本次原生截图不带 cICP/gAMA/sRGB/ICC。用 FFmpeg 直接解码这些 PNG，读取的是存储的 RGB 数字；把它们加载至 Chrome Canvas，读取的是浏览器经过色彩管理后的 sRGB。

实际 UI 测试中，同一背景点 `(640,359)`，IINA 截图在 Canvas 取到 `#30302F`，FFmpeg PNG 在 Canvas 取到 `#252525`。这证明 **原始 PNG RGB 很接近并不等于实际截图取色一致**。此发现只说明本轮两种 PNG 导出方式的差异，不能据此认定用户之前的视频一定受这个因素影响。

更接近用户需求的比较使用 **同一 IINA**：一张为视频外挂 ASS 预览，一张为 FFmpeg 压制后的 H.264 成片。两张均使用同样的 IINA 原生 PNG 导出，再在同一 Chrome 校准界面逐个实点采样 24 色，均为 5×5 中位数：

| 比较 | 最大单通道误差 / 255 | RGB 通道 RMS / 255 |
| --- | ---: | ---: |
| 同一 IINA 导出、同一 Chrome sRGB 取色：外挂 ASS vs 压制成片 | 2 | 0.707 |
| 同一 IINA 导出、Python 原始 RGB 取色：外挂 ASS vs 压制成片 | 2 | 0.736 |
| IINA 外挂 ASS PNG vs FFmpeg PNG：仅 Python 原始 RGB | 1 | 0.687 |

橙色色块的浏览器实点结果为 `#EB8330` vs `#EA832F`。完整浏览器样本通过工具自己的导出按钮保存，保存在本地 `output/browser-iina-pair-profile.json`。

没有进行 macOS 桌面截图/显示器 ICC、用户截图软件、HDR、真实项目、半透明文字及重采样边缘的验收，也没有改用户的播放器/显示器偏好。

## 矩阵与映射的独立实验

下面均比较 **Python 原始 RGB**，目标是 IINA 外挂 ASS 在 Matrix None 下的原生色块；不能把此表当成浏览器/屏幕取色表。

| FFmpeg 路径 | 最大单通道误差 / 255 | RGB 通道 RMS / 255 |
| --- | ---: | ---: |
| ASS `None`，原样 RGB | 1 | 0.687 |
| ASS `TV.709`，匹配本次 BT.709 视频 | 1 | 0.687 |
| ASS `TV.601` 或缺少头部，相对 Matrix None 目标 | 39 | 8.830 |
| 原 `None` 路径套用旧经验公式 | 11 | 5.964 |
| 原 `None` 路径使用本次仿射补偿后重新渲染 | 2 | 0.791 |

同一个 `TV.601`/缺失头部的 ASS 在 IINA 与 FFmpeg 8.1 中都产生类似历史矩阵转换，两者之间最大误差 1；上表的 39 是它们相对 **原样目标 RGB** 的差异，不能称为 IINA 与 FFmpeg 之间的误差。

本次仿射拟合的训练 RMS 为 0.524、逐个留出 RMS 为 0.639，但真正重渲染 RMS 0.791，**没有优于原样基线 0.687**。这正是默认保留原样转换的原因：整数 YUV 量化、截断和非线性使数学预测不等于渲染验收。校准功能供实际有系统偏差的流程收集和验证映射，不能保证一定改善。

另外，查阅 FFmpeg 官方 n7.1 与 n8.1 源代码发现其字幕绘制矩阵处理不同。因此，以上 8.1 结果不应倒推为旧工具开发时 FFmpeg 的实际行为。
